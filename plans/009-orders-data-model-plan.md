# Plan 009: Orders data model

- Number: 009
- Created: 2026-11-04
- Spec: [.specs/009-orders-data-model.md](../.specs/009-orders-data-model.md)

## Concept summary

No open question; the spec lists every column and every rule the database must enforce. Choices made in this plan, each recorded in `adrs/orders-data-model.md`:

1. **One migration**, `V3__create_orders_tables.sql`, with a named constraint per rule so a failure reads well: `ck_orders_status`, `ck_orders_payment_method`, `ck_orders_state_two_uppercase_letters`, `ck_orders_total_is_subtotal_plus_fee`, `ck_order_items_quantity_between_1_and_99`, `uq_order_items_order_coffee`, and so on.
2. **`orders.id` is a UUID** (generated by the database when not given). **`order_items.id` is `BIGINT GENERATED ALWAYS AS IDENTITY`**: the spec only says `id`, and an increasing id gives the lines of an order a stable order (insertion order) with no extra `position` column, so `GET /api/v1/orders/{id}` returns lines in the order they were created.
3. **Foreign keys**: `order_items.order_id` references `orders` with `ON DELETE CASCADE`; `order_items.coffee_id` references `coffees` with `ON DELETE RESTRICT`. A coffee can never disappear from a past order; the name and price are copied into the line (`coffee_name`, `unit_price_in_cents`).
4. **Money is `INTEGER` cents.** Checks: `delivery_fee_in_cents >= 0`, `subtotal_in_cents >= 0`, `unit_price_in_cents >= 0`, `total_in_cents = subtotal_in_cents + delivery_fee_in_cents`, and, beyond the spec, `line_total_in_cents = unit_price_in_cents * quantity`, because a line total that disagrees with its parts is the same kind of corruption the spec guards against. The sum of the lines equal to `subtotal_in_cents` cannot be a column check; the use case guarantees it and a test of spec 010 verifies it.
5. **The `status` check allows only `confirmed`**, as specified (no history, no other states).
6. **The payment method values are repeated in the database** (`credit_card`, `debit_card`, `cash`); a test inserts one order per `PaymentMethod` constant, so the enum and the check cannot drift apart.
7. **The end-to-end test** (`OrdersMigrationE2ETest`) uses plain SQL against the Testcontainers PostgreSQL, one assertion per rule, and deletes what it inserted after each test because every end-to-end class shares one database.
