- Number: 004

## Concept summary

No open question; the spec lists every table, constraint, row, and tag count. Choices made in this plan, each recorded in `adrs/catalog-data-model.md`:

1. **Plan numbers follow the spec numbers** (004 for spec 004), as plans 003 and 012 already do. `RULES.md` describes an independent sequence; following it would give 013 to this plan and collide with the plans written for the app specs from another environment.
2. **Two migrations**, as in the spec: `V1__create_catalog_tables.sql` (schema) and `V2__seed_catalog.sql` (data). Named constraints, so a failure reads well.
3. **Identifiers are UUIDs generated by the database** (`gen_random_uuid()`, built into PostgreSQL 13 and later). The seed does not fix ids; `coffee_tags` is filled by joining on slugs, so the seed does not depend on any generated id.
4. **`tags.position` is unique too** (the spec only asks for a `position`): the tag order is part of the response contract (spec 005), so two tags with the same position would make it ambiguous.
5. **The end-to-end test runs on the real application context** (Flyway runs at startup) against the Testcontainers PostgreSQL, and asserts every acceptance criterion with plain SQL. `PostgresContainerSupport` becomes public so tests outside `com.coffeedelivery.e2e` reuse the same container.
6. **Re-running the migrations** is tested through the `Flyway` bean: `validate()` passes and `migrate()` executes zero migrations.
