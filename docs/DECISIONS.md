# Architectural decisions and their reasoning

The 40 decision records in [`adrs/`](../adrs) say what was decided. This page is the map: the decisions that shape the product, **why** each was taken, what it costs, and what was left out on purpose (taken from the "What not to do" of the specs and from the records). Each row links to the record with the full list.

How a decision is made here: a spec states the outcome and what not to do; the plan lists the choices; the AI proposes, the owner approves; the record is written when the decision is verified by tests (the status of every record is "Accepted and verified"). Decisions that were reversed or refined are marked.

## 1. Shape of the system

| Decision | Why | Cost or trade-off | Record |
| --- | --- | --- | --- |
| **Vertical slices with four layers** (`domain`, `application`, `infrastructure`, `interfaces`) in the API, enforced by ArchUnit | Each business flow changes in one place; the domain can be read and tested without Spring; a rule written in a document tends to rot, a failing build does not | More files for a small product (one use case class per flow, one handler per endpoint) | [api-foundation](../adrs/api-foundation.md), [architecture-rules-and-page-composition](../adrs/architecture-rules-and-page-composition.md) |
| The layer is called `interfaces`, not `interface` | `interface` is a Java keyword and cannot be a package name | The docs and agents use the new name | [api-foundation](../adrs/api-foundation.md) |
| **Slices do not import each other's outer layers**; `orders` reads prices through its own port `CoffeePriceLookup` | `orders` can be split from `catalog` later without untangling imports | Its own SQL on the shared database | [orders-create](../adrs/orders-create.md) |
| `application` may use `@Service` and the `shared.error` exceptions, nothing else of Spring or the web | All five use cases were already `@Service`; removing it would only move the Spring knowledge elsewhere. A line had to be drawn and then guarded | The rule is stricter than common practice; a job needed an exception (see below) | [architecture-rules-and-page-composition](../adrs/architecture-rules-and-page-composition.md) |
| A **scheduled job is an entry point** of a use case, like a request handler | The retention job runs a use case with no HTTP request; "one handler per use case" became "one handler or job" | The rule changed after the first version, and says so | [orders-address-retention-and-rate-limit](../adrs/orders-address-retention-and-rate-limit.md) |
| **No accounts, no sign-in** | The product is a store where the order is paid on delivery; accounts are listed as out of scope in [BUSINESS.md](../.docs/BUSINESS.md). The order is a public resource addressed by an unguessable UUID | Anyone with the id can read an order, which is why the address is removed after 90 days and the limit exists | [orders-get](../adrs/orders-get.md), [orders-address-retention-and-rate-limit](../adrs/orders-address-retention-and-rate-limit.md) |
| Monorepo with one Yarn workspace (`apps/app`) and a Gradle project (`apps/api`) | One repository, one set of rules and commands (`yarn code:fix`, `lint`, `types:check`, `test`, `test:e2e`, `build`) for both | Two build tools | [foundation](../adrs/foundation.md) |

## 2. Data and money

| Decision | Why | Cost or trade-off | Record |
| --- | --- | --- | --- |
| **Money is integer cents everywhere** except on screen; a test forbids `double`, `float`, and `BigDecimal` in the domain | No rounding errors; a total is a sum of integers | Formatting is a separate, tested function | [catalog-data-model](../adrs/catalog-data-model.md), [architecture-rules-and-page-composition](../adrs/architecture-rules-and-page-composition.md) |
| **The server owns prices and totals**; the client sends ids and quantities, never prices | A tampered price has nothing to change; one rule | The summary needs the server's quote | [orders-create](../adrs/orders-create.md), [orders-quote-endpoint](../adrs/orders-quote-endpoint.md) |
| **One rule for the totals** (`OrderTotals`), used by the order and by the quote; `pricing.ts` removed from the app | The number the customer sees is the number charged, and a fee by zone changes one place. Proved at four levels (domain, use case, e2e, browser) | One request more for each change of the cart | [orders-quote-endpoint](../adrs/orders-quote-endpoint.md) |
| **A price snapshot in each order line** | Changing the catalog never alters a past order | Names and prices are stored twice | [orders-data-model](../adrs/orders-data-model.md) |
| Business rules also as **named database constraints**, tested one assertion per rule | The database is the last guard: it holds when a second entry point forgets to validate | Rules in two places (the validator and the schema), kept equal by tests | [orders-data-model](../adrs/orders-data-model.md) |
| Ids are UUIDs generated by the database for the catalog; `order_items.id` is an identity | Safe ids for public URLs; an increasing id keeps the order of the lines without a position column | Seed ids differ per database, so clients read ids from the API | [catalog-data-model](../adrs/catalog-data-model.md), [orders-data-model](../adrs/orders-data-model.md) |
| **Hand-written validation in `interfaces`**, not Bean Validation | The messages, the JSON paths (`items[0].quantity`), the strict quantity, and the "whole number" rule are all custom; a plain class is simple to unit test and adds no dependency | More code than annotations | [orders-create](../adrs/orders-create.md) |

## 3. Reliability

| Decision | Why | Cost or trade-off | Record |
| --- | --- | --- | --- |
| **Idempotent order creation decided by a unique index**, with a fingerprint of the request | A lost answer invites a second click and a duplicate order (a wasted trip, because the order is paid on delivery). The database decides, so it holds in parallel and with several API instances (tested with 8 threads) | Keys are kept with the order; no expiry. Left out on purpose: storing the response, an expiry, a cache | [orders-idempotent-create](../adrs/orders-idempotent-create.md) |
| The checkout **keeps one key while the request is identical** and makes a new one when it changes | A retry replays safely; a changed order never hits the conflict | A small pure unit to maintain | [orders-idempotent-create](../adrs/orders-idempotent-create.md) |
| **One batch for the order lines, one read-only transaction for the catalog** | The slowest route did N+1 statements; measured: p95 17 to 27 ms down to 10 to 12 ms | Left out on purpose: a cache, an `ETag`, paging | [api-batch-and-read-transactions](../adrs/api-batch-and-read-transactions.md) |
| **A default method on a repository interface is not allowed** (found by a failing test) | Spring does not apply the class-level `@Transactional` to a method that the interface declares | A documented rule | [orders-idempotent-create](../adrs/orders-idempotent-create.md) |
| **The rate limit is at the proxy, not in the API** | A limit in the process does not hold with more than one instance | It does not apply to the dev server; behind a load balancer the real client address must be passed on | [orders-address-retention-and-rate-limit](../adrs/orders-address-retention-and-rate-limit.md) |
| **Addresses are cleared after 90 days** by a Spring `@Scheduled` job and one `UPDATE ... WHERE address_cleared_at IS NULL` | The address has no use after delivery and the days of a complaint; the same statement makes a second run or a second instance harmless. Left out on purpose: deleting orders, a scheduler library, a lock table | The job runs on each instance | [orders-address-retention-and-rate-limit](../adrs/orders-address-retention-and-rate-limit.md) |

## 4. Observability and operation

| Decision | Why | Cost or trade-off | Record |
| --- | --- | --- | --- |
| **Grafana LGTM and OpenTelemetry from the first endpoint**; structured JSON logs; a dashboard provisioned from a file | Observability added later is never complete. A file can be reviewed and tested; a UI edit cannot | Logs are not shipped to Loki; no JDBC spans ([OBSERVABILITY.md](OBSERVABILITY.md)) | [api-foundation](../adrs/api-foundation.md), [api-observability-and-load-tests](../adrs/api-observability-and-load-tests.md) |
| **Metric names read from the running Prometheus**, not guessed; the percentile histogram is pinned by a test | A query written for `_seconds_` would return nothing silently | The tests know the names | [api-observability-and-load-tests](../adrs/api-observability-and-load-tests.md) |
| **Business counters** (`orders.created`, `orders.addresses.cleared`) next to the HTTP metrics | HTTP counts cannot tell a retry from a new order or show that the retention job ran | The handler owns one counter (a review noted that a port in `application` would be cleaner; recorded in the backlog) | [testing-and-observability-evidence](../adrs/testing-and-observability-evidence.md) |
| k6 profiles with **think time** and shared thresholds; every endpoint has a scenario | Without think time one virtual user sent about 1,500 requests per second and the profile measured the load generator | A root test guards it | [api-observability-and-load-tests](../adrs/api-observability-and-load-tests.md) |
| **Two images, pinned bases, non-root, no secrets**; a backup and a restore that never touches the live database, with a drill | No real user before the orders can be recovered. The restore goes only into `restore_check` and compares counts | No host, registry, or deployment: that is the owner's choice | [packaging-and-backup](../adrs/packaging-and-backup.md) |
| **A CI pipeline that repeats `yarn ci`** (one list of commands used twice) | The pipeline and the developer run the same thing; pinned actions and Node 22.22.2 | Node 22.22.2 is the least the dependencies accept | [ci-pipeline](../adrs/ci-pipeline.md) |
| Local infra pinned (`postgres:18.6-alpine`, `grafana/otel-lgtm:0.39.0`), ports on `127.0.0.1`, no defaults in Compose | A bump is a deliberate edit; the database and an anonymous-admin Grafana stay off the network | Required variables must exist (`yarn env:setup`) | [local-infrastructure](../adrs/local-infrastructure.md) |

## 5. The app

| Decision | Why | Cost or trade-off | Record |
| --- | --- | --- | --- |
| **The cart is client state** (a pure reducer, `localStorage`, ids and quantities only) | No server cart without a user to attach it to; a saved cart never shows a stale price | Not shared between tabs or devices | [cart-state](../adrs/cart-state.md) |
| **TanStack Query and an own `fetch` client** with an `ApiError`; no retry for a 4xx, at most two for others | A wrong request is not fixed by retrying; no HTTP library | Own client to maintain | [app-foundation](../adrs/app-foundation.md) |
| **Vite proxy instead of CORS** in development, nginx proxy in the image | One origin, no CORS configuration | The proxy must be kept in step | [app-foundation](../adrs/app-foundation.md) |
| **Lazy checkout and order routes, WebP images made by a script** | The entry chunk went from 522 kB to 238 kB; images from 1.82 MB to 137 kB; Lighthouse 91 to 100. Left out on purpose: CDN, service worker, AVIF, a bundle analyzer | The first visit to checkout waits for a chunk | [app-lighter-first-load](../adrs/app-lighter-first-load.md) |
| **Pages only compose features**; shared `LoadingState`, `ErrorState`, `TextLink`; one quantity limit; one set of e2e helpers | The audit found four copies of the same blocks; a change is now made once | Three more components | [app-shared-ui-blocks](../adrs/app-shared-ui-blocks.md), [architecture-rules-and-page-composition](../adrs/architecture-rules-and-page-composition.md) |
| **Design parity measured**, not judged by eye: tokens from Figma, a 2% pixel limit with named masks, and layout boxes within 2 px | "Looks like the design" is not a test | Masks must be maintained, and each one is named | [app-visual-parity](../adrs/app-visual-parity.md), [app-design-tokens](../adrs/app-design-tokens.md) |
| **Accessibility as a test** (axe in every component test and in the browser, 24 by 24 px targets, six viewports) | WCAG 2.2 AA is a rule of the project, so it must fail a build | Contrast is below AA in some pairs of the owner's palette; this is recorded, not hidden | [app-base-components](../adrs/app-base-components.md), [app-responsive](../adrs/app-responsive.md) |
| **The counter of a card keeps its value after adding, with a badge of how many are in the cart** (reverses the first choice, to reset to 1) | The owner reported on 2026-11-11 that after adding 3 coffees the card showed 1 again, which hid what had just been added | Adding again adds the counter again, and the badge shows the total | [cart-add-from-card](../adrs/cart-add-from-card.md), [testing-and-observability-evidence](../adrs/testing-and-observability-evidence.md) |

## 6. The way of working (with AI)

| Decision | Why | Record |
| --- | --- | --- |
| **One spec, one plan, one decision record, one commit** | Every change can be traced from a requirement to its tests and its reasoning | [foundation](../adrs/foundation.md) |
| **Specialist agents that only read** (`code-reviewer`, `structure-auditor`, `performance-analyst`, `evolution-advisor`, `bug-investigator`) and one that edits only documents (`docs-keeper`) | The finding and the fix are separate decisions; an agent that cannot edit cannot hide a change | [AGENTS-IN-ACTION.md](AGENTS-IN-ACTION.md) |
| **Skills for the workflow** (`implement-me`, `create-specification`, `commit-and-push`, `tdd`, and others) | The same process every time, written down | [.docs/AGENTS.md](../.docs/AGENTS.md) |
| **Evidence by command, not by claim**: each ADR has a "verified" part with the commands and numbers | A decision is accepted when a test or a measurement shows it works | every record |

## 7. Open decisions (the backlog the audits produced)

From the `structure-auditor` report of 2026-11-13 ([AGENTS-IN-ACTION.md](AGENTS-IN-ACTION.md), example 2): extract a hook from the 104-line `OrderSummary`; move the order invariants (quantity range, address format) into the domain so a second entry point cannot create an invalid order; put business metrics behind a port in `application`; move the `Order` types out of `checkout/api.ts`; make the domain rule an allow-list. None is a defect today; each needs its own spec, which is why they are listed and not done.
