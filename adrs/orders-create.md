# ADR: Orders, create an order

- Status: Accepted and verified
- Date: 2026-11-04
- Spec: [.specs/010-orders-create.md](../.specs/010-orders-create.md)
- Plan: [plans/010-orders-create-plan.md](../plans/010-orders-create-plan.md)

## Context

The cart lives in the browser, so the server receives coffee ids, quantities, the address, and the payment method. It must never trust a price from the client, and an order is stored whole or not at all.

## Decisions

1. **The totals rule is in the domain.** `Order.place(...)` sums the line totals (`unitPrice * quantity`), takes the fee from `DeliveryPolicy` (spec 007), and adds them. `OrderItem`, `Address`, and `OrderStatus` are records and an enum with no Spring and no JSON. The example of the spec (1 + 2 coffees at 990 plus 350) is a test at three levels: domain, use case, and end to end.
2. **`CreateOrderUseCase` prices from the catalog through its own port.** `CoffeePriceLookup` (owned by `orders`, implemented by `JdbcCoffeePriceLookup` with its own SQL on the shared database) means `orders` never imports `catalog`; `ArchitectureTest` stays green. An id that is not in the catalog gives `422 unprocessable_content` with `fields.items` naming it, and nothing is saved.
3. **The client never sets a price.** The request records have no price field, and unknown properties are dropped, so `priceInCents`, `unitPriceInCents`, or `totalInCents` anywhere in the body is accepted and ignored (tested in the handler and end to end).
4. **Atomic save.** `JdbcOrderRepository` is `@Transactional`: the order row and every line commit together. The test saves an order whose second line points at a coffee that does not exist and checks that no order and no line remain.
5. **Validation is hand-written in `interfaces`** (`CreateOrderRequestValidator`), not Bean Validation. The paths (`items[0].quantity`), the messages, trimming, the blank-to-null complement, and the "whole number" rule are all custom, and a plain class is easy to unit test (16 tests). It reports every problem at once. This avoids a new dependency (`spring-boot-starter-validation`).
6. **Strict quantity.** `quantity` is read as a JSON node and must be an integral number from 1 to 99: `"2"`, `1.5`, `2.0`, `null`, `true`, and `{}` are rejected, which Jackson would otherwise coerce silently.
7. **Wrong JSON types name their path.** `ApiExceptionHandler` now reads the path of the value Jackson could not read (`MismatchedInputException`, for example `items[1].quantity`) and answers `400 validation_failed` with that key and a fixed message, instead of the generic `body` key. Invalid JSON syntax or a missing body still gives `fields.body`. The message never carries the exception text.
8. **Shared error classes.** `FieldsException` is the base of `ValidationFailedException` (400, from spec 006) and the new `UnprocessableContentException` (422); `NotFoundException` (404) is for spec 011. All are mapped in `ApiExceptionHandler`, in `shared.error`, so every error is still built in one place.
9. **Time and ids.** A `Clock` bean (`shared.config`) makes `createdAt` testable. The instant is cut to microseconds because PostgreSQL stores microseconds, so the `201` body equals the later `GET` body (spec 011). The order id is generated by the application.
10. **Response.** `OrderResponse` is a package-private record shared by create and get. `complement` is always present, `null` when there is none. `201` carries `Location: /api/v1/orders/{id}`.
11. **k6.** `orders-create.js` posts 1 Latte and 2 Cuban and checks `201` and a total of 3320. Coffee ids are read once per virtual user (`lib/catalog.js`) because they differ between databases. Every iteration stores an order, so a local load run leaves rows behind (documented in the load README).

## Consequences

- Any new endpoint that rejects input can throw `ValidationFailedException` or `UnprocessableContentException` from its use case and inherit the error shape.
- Orders created by manual checks and load runs stay in the local database until it is reset.
- No idempotency key: sending the same request twice creates two orders (out of scope in the spec).
- No new library.
