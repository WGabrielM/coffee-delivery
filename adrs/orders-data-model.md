# ADR: Orders data model

- Status: Accepted and verified
- Date: 2026-11-04
- Spec: [.specs/009-orders-data-model.md](../.specs/009-orders-data-model.md)
- Plan: [plans/009-orders-data-model-plan.md](../plans/009-orders-data-model-plan.md)

## Context

A confirmed order must keep its totals correct forever, even when the catalog changes later. The database is the last line of defense, so it refuses every inconsistent row.

## Decisions

1. **One migration, `V3__create_orders_tables.sql`, with a named constraint per rule** (`ck_orders_status`, `ck_orders_payment_method`, `ck_orders_state_two_uppercase_letters`, `ck_orders_total_is_subtotal_plus_fee`, `ck_order_items_quantity_between_1_and_99`, `uq_order_items_order_coffee`, and so on), so a violation names the rule in logs and tests.
2. **A price snapshot in each line.** `order_items` copies `coffee_name` and `unit_price_in_cents`, so changing the catalog never alters a past order. `coffee_id` is kept with `ON DELETE RESTRICT`: a coffee that was ordered cannot be deleted. Deleting an order deletes its lines (`ON DELETE CASCADE`).
3. **`order_items.id` is a `BIGINT` identity**, not a UUID: the spec only says `id`, and an increasing id gives the lines of an order a stable order (insertion order) with no `position` column, which the `GET` endpoint of spec 011 relies on. `orders.id` is a UUID (generated by the database when not given), because it appears in URLs.
4. **Money is `INTEGER` cents.** Checks: the fee, the subtotal, and the unit price are not negative; `total = subtotal + fee`; and, beyond the spec, `line_total = unit_price * quantity`, because a line that disagrees with its parts is the same kind of corruption. The subtotal equal to the sum of the lines cannot be a column check; the use case guarantees it (spec 010).
5. **Only the status `confirmed`** is allowed (no history, no tracking). **The three payment methods are repeated in a check**; `OrdersMigrationE2ETest` inserts one order per `PaymentMethod` constant, so the enum and the check cannot drift apart.
6. **`complement` is the only nullable column** of `orders`.
7. **Two indexes beyond the keys**: `uq_order_items_order_coffee (order_id, coffee_id)` (also serves lookups by order) and `ix_order_items_coffee_id`, which keeps the foreign key check cheap when a coffee is deleted.
8. **The test** (`OrdersMigrationE2ETest`, 23 tests) uses plain SQL on the Testcontainers PostgreSQL, one assertion per rule, and deletes its orders after each test because every end-to-end class shares one database.

## Consequences

- Specs 010 and 011 read and write these tables with their own SQL in `orders.infrastructure`.
- A changed rule (for example a new payment method) needs a new migration and a change to `PaymentMethod`; the test fails until both agree.
- No new library.
